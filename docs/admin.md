# BuBu-后台管理

2026-10-08：已完成本地验收，并随 `20261008T055817Z` 发布到正式 HTTPS 站点 `/admin/`。管理端位于根目录 `admin/`，与画布 `frontend/`、Go 服务 `backend/` 并列；独立构建，共用后端、用户、会话和积分账本。

## 功能与请求链路

- 管理员邮箱密码登录、会话恢复、退出。
- 全部用户分页，邮箱包含搜索／完整用户 ID 搜索；显示注册时间、角色、状态、可用和冻结积分。没有积分账户的旧用户显示为 0。
- 用户详情抽屉：正整数测试积分发放、原因、二次核对与该用户的全部积分流水。
- 单次发放 1～10,000 分；原因去除两端空白后为 1～200 个 Unicode 码点。已停用用户不能收到新的发放。

```text
管理页面 /admin/
→ Go /api/admin/*：Session 身份检查 + 实时管理员角色检查
→ 写请求继续检查来源、CSRF、当前会话用户
→ 发放事务：重新检查管理员 → 锁定目标积分账户 → 核对请求编号
→ 原子增加可用积分 + 写入管理员、原因和发放流水
→ 提交 → 返回余额及流水 → 管理端刷新；画布下次读取余额即可看到新积分
```

发放增加可用积分，冻结余额由已有生成任务流程维护。本版提供发放和只读账本；账号禁用、角色管理、密码重置、人工解冻、支付充值没有管理页面或操作接口。

## 身份与权限

继续使用服务端 Session + HttpOnly Cookie，不使用 JWT。密码验证沿用 Argon2id；浏览器持有随机 Session 凭证，PostgreSQL `user_sessions` 只保存其 SHA-256 哈希。正式 HTTPS 使用 Secure Cookie；来源与 CSRF 机制沿用画布端。`X-Session-User` 只用于检测标签页账号切换，不能指定或冒充身份。

`users.role` 有 `user`、`admin` 两种值，迁移和普通注册都默认 `user`。每次会话解析都从数据库读取当前角色和账号状态。`/api/admin/auth/login` 只接受已存在且 active 的管理员：未知邮箱不会注册，普通账号不会升级。管理员登录和普通登录共用限流及会话创建机制。

管理员仍受原有画布所有权约束；管理权限仅开放本版用户与积分管理接口，没有绕过私有画布／素材权限。

同一正式站点下，画布和管理端共用登录会话：换账号登录会替换浏览器 Cookie，退出会撤销当前会话；同源标签页使用 BroadcastChannel 通知失效。本机 5173 与 5176 属于不同来源，Cookie 仍按主机共享，但 BroadcastChannel 不跨端口；下一次 API 的 Session／CSRF／`X-Session-User` 检查阻止旧页面继续使用已变化的身份。凭证不写入 localStorage。

## 数据模型与一致性

迁移 `007_admin.sql` 不新增业务表：

| 位置 | 变化与职责 |
| --- | --- |
| `users.role` | 普通用户／管理员角色约束；新增注册时间、ID 排序索引 |
| `credit_accounts` | 继续维护每个用户的可用与冻结余额 |
| `credit_ledger.source` | `signup` 注册赠分、`manual` 管理员发放、`legacy` 原手动工具／历史发放、`system` 生成冻结／结算／退回 |
| `credit_ledger.actor_user_id` | 发放操作者的用户外键；历史记录不补造操作者 |
| `credit_ledger.reason` | 发放备注；数据库约束要求 manual 流水具有操作者和有效原因 |

迁移按已知注册幂等键识别已有注册赠分，其他旧 grant 标为 legacy；不改动任何积分数量。管理员信息和备注仅在管理接口返回，普通用户的流水接口保持原有字段。

发放与生成冻结在同一积分账户行上串行写入，因此并发时不会覆盖彼此的余额。余额增加、流水和审计字段在同一 PostgreSQL 事务提交；插入流水失败会回滚余额。事务内重新读取管理员角色并持有用户行共享锁，保证发放提交期间角色与状态稳定。

每次确认发放生成一个 UUID，流水唯一键为 `admin-grant:<requestId>`。同一个编号、目标、管理员、数量和原因重试，返回原流水和当前余额；改变输入复用编号返回 409。相同目标的重试先锁账户、再核对流水，避免并发重复入账。不同编号代表独立业务操作，可以向同一用户多次发放。

管理端在发送前把待确认操作保存在本标签页的 sessionStorage，以管理员 ID 隔离。网络断开、服务异常或登录失效时保留编号；刷新或重新登录同一管理员后可核对／重试。在结果确定前阻止开启下一笔发放。收到明确成功响应后清除。这里保存的是操作数据，不是会话凭证；关闭标签页或清除站点存储会丢失待确认信息，此时先核对积分记录再决定是否发新的一笔。

## 接口契约

除登录外，以下管理接口均需有效 Session 和 admin 角色。读取响应禁止缓存。

| 接口 | 输入／结果 |
| --- | --- |
| `POST /api/admin/auth/login` | `{email,password}`；返回 `{user:{id,email,role},csrfToken,expiresAt}` 并设置 HttpOnly Cookie；需允许的 Origin 和 `X-Requested-With: frame-space` |
| `GET /api/admin/me` | `{session,maxGrantPoints,maxReasonLength}` |
| `GET /api/admin/users?q=&limit=20&offset=0` | `{users,total,limit,offset}`；每位用户含 `id,email,role,status,createdAt,available,reserved` |
| `GET /api/admin/users/:id/ledger?limit=20&offset=0` | `{user,entries,hasMore}`；流水包含余额变化、变化后余额、来源、操作者、原因和任务 ID |
| `POST /api/admin/users/:id/credits` | `{points,reason,requestId}`；返回 `{account,entry,replayed}`，首次和重试均为 200 |
| `POST /api/auth/logout` | 复用会话退出接口，成功 204；需来源与 CSRF 校验 |

分页 `limit` 为 1～100，`offset` 为 0～100000；搜索最长 254 字符。用户按注册时间／ID 倒序，流水按 ID 倒序。未登录 401，非管理员 403，参数错误 400，不存在的有效用户 ID 为 404，请求编号冲突或目标停用 409。请求体中的管理员身份、余额或角色不参与授权。

## 首个管理员初始化

先备份目标数据库并应用迁移。核对账号对应的 UUID 后，在后端目录使用服务器工具：

```powershell
go run ./cmd/set-admin --user-id <已核对的用户UUID>
go run ./cmd/set-admin --user-id <已核对的用户UUID> --apply
```

第一次是只读预览，不运行迁移、不改变权限；第二次显式授权，事务内撤销该账号的已有会话，要求重新登录。已是管理员的账号重复执行不会重复撤销会话。该工具只读取后端 `DATABASE_URL`，没有公开的角色修改 HTTP 接口，不按未经验证的邮箱自动提升权限。
